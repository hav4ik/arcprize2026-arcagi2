# B32-M OOM modes (2026-10-30)

Why the B32-M submission (Manh's vLLM fork, DCP4, LB 46.5) most likely failed, and what we do differently. Page version:
https://claude.ai/artifact/VpLWKS32R9rbRrausrp2jW (private).

**Most likely cause: a GPU out-of-memory a few hours into the scored run.**
- In Manh's fork, one CUDA OOM kills the whole engine.
- B32-M's solver then spent its retries on the dying server, so most of the remaining work was lost.
- Host RAM is ruled out.
- **Reproduced 2026-10-30 05:37 UTC:** the 12 h pod replica with Kaggle-matched GPU headroom
  (`experiments/E062_manh_vllm_fork/per_layer/pod3_runs/b32m_v3/`) hit a CUDA OOM 2.11 h into its run.
  - It happened on GPU 3, in an all-gather that asked for 32 MiB with 20.06 GiB allocated under a 20.37 GiB cap.
  - The pods run faster than Kaggle, so the same point comes later on Kaggle's clock.
- Not yet excluded: a CUDA illegal memory access, which Manh hit on Kaggle at 120 concurrent requests
  (`notes/2026-10-30_illegal_memory_access_risk.md`, pending).

## How the margin disappears

1. **The KV pool is sized from a startup profile that misses long-context steps.**
   - DeepSeek-V4.1's sparse-attention indexer and decode logits grow with context length.
   - B32-M's wheel (`5e1bccd07c`) predates the fork's profiling fixes (`f506afa210`, `7ab756940a`), so it sized the pool as
     if those steps were free.
2. **Kaggle's startup leaves less room than the pods.**
   - CUDA graphs took 0.65 GiB on Kaggle vs 0.34 GiB on pods; add util 0.945 and DCP4.
   - Kaggle's cap sat 0.67-0.73 GiB above reserved memory (pods: 1.16-1.22), which is 0.06-0.12 GiB below the profile's
     own peak.
3. **After warm-up the fork caps PyTorch** at reserved + free − 0.5 GiB, so a stray allocation outside PyTorch can't
   fill the GPU. Every later working buffer has to fit under that fixed line.
4. **Peaks grow as contexts lengthen.** On the replica:
   - the first 10 minutes ate 0.4 GiB of spare room (0.95 → 0.55);
   - the first allocator retry (a cache flush) came at 1.26 h;
   - a retry storm followed at 1.7 h (9 → 23 retries in 10 minutes);
   - by 2.0 h the peak was growing faster (+0.09 GiB/h, up from +0.07), with 0.42 GiB left and 34 retries.
   - At 2.11 h the replica hit a CUDA OOM. The Kaggle run stopped answering at ~4.85 h.
5. **It runs out before zero.** Memory gets stranded in partly used allocator segments.
   - Our local lab OOMed with 0.39 GiB nominally free, because 0.53 GiB was stranded (`notes/2026-10-30_vllm_lab_memory.md`).
   - So the danger band starts around 0.26 GiB.
6. **One OOM ends the engine.**
   - vLLM has no per-request OOM recovery (`notes/2026-10-30_vllm_failure_paths.md`).
   - Every in-flight attempt loses its progress, and B32-M's solver counted the dying server's HTTP 500s as failed tries.

## OOM modes we have seen

| Mode | What happens | Earliest signal | Where seen |
|---|---|---|---|
| Peak growth | A long-context step needs more working memory than the cap allows | Allocator retries; spare room sliding | B32-M replica (OOM at 2.11 h); B32-M on Kaggle (inferred) |
| Stranded memory | Partly used segments block a large request although free bytes exist | OOM with spare room still above 0 | Local lab; the fork at util 0.95 after 70 min (254 MiB request, 695 MiB stranded; commit `46a2cb33de`) |
| Outside PyTorch | A kernel module (Humming) loads when PyTorch has taken the whole GPU | OOM on the first prefill of a new size | The fork before the cap (fixed by cap + reserve, commit `b9ad670a67`) |
| Large re-prefill | An evicted long request is prefilled again in one big step | Prefill bursts at high KV use | Manh's diagnosis of his OOMs |
| Host RAM (not the cause) | Shared memory flat at ~125 GiB, 19-24 GiB under Kaggle's 173 GiB | Container memory trend | All replicas |

## What we do from now on

- **Pin the KV pool** with `--kv-cache-memory-bytes`, sized from Kaggle's own startup numbers, so pods and Kaggle get the
  same margin. Util alone shifts with CUDA graphs and compile caches.
  - Check first that the fork honours the flag.
- **Keep spare room under the cap above stranded memory + 0.3 GiB** on the worst GPU after warm-up, ideally ≥ 0.75 GiB.
  - For B32-M's settings, util 0.02 lower would have been enough.
- **Only ship wheels whose startup profile covers long-context steps.**
- **Watch cap − reserved, not only cap − peak.** On the replica, reserved memory crept to 0.03 GiB below the cap
  (expandable segments) before a 32 MiB request failed, while cap − peak still read 0.40 GiB.
  - Treat the first allocator retry, and cap − reserved under ~0.15 GiB, as alarms (`kaggle/reliability/`).
- **Make a death cheap:** a restart supervisor, plus a solver that re-queues attempts for free on 500s and timeouts
  (`kaggle/dsv41_tools/MANH_SAFETY_EDITS.md`, branch `havu-s27-graceful-recovery`).
