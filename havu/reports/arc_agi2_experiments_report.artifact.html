This report collects every model and harness experiment we have run on ARC-AGI-2 so far. Models: DeepSeek V4.1-Flash, its replacement V4.1-Flash-1017 (served as deepseek-flash from 2026-10-17) and V4-Pro (DeepSeek API); Qwen3.8-27B (NVFP4 and FP8 checkpoints on self-hosted SGLang/vLLM, on Kaggle 4×L4 and on rented boxes, INT4/AWQ variants, and a LoRA SFT on DeepSeek tool rollouts) and Qwen3.6-35B-A3B; MiniCPM-V-4.7-35B-A3B and LFM2.5-24B-A2B (self-hosted); Nemotron 3.5 Lightning and Nemotron 3 Super 120B (OpenRouter) and Nemotron-3.5-Bolt (self-hosted, 2-bit experts). Harnesses: a no-tool single call with the ARC Prize prompt; a generation API harness for Qwen that continues the raw completion through mid-thought EOS and forces a final answer at the budget; Python tool use in grid mode (answer as a grid, later handed over with submit_answer) and code mode (submit_solution, checked on the train pairs); token-budget variants of the tool harness (hard caps, budget notes, soft targets, thinking-off turns); E017's additions to it (a host-computed task summary, a roles prompt, session helpers, a live train check and a conditional 3rd attempt); E016's "time is up" continuation of cut-off attempts; E029's "decide in code" prompt with a turns-left note; the Qwen program agent (submit_program, train-checked, E019/E020) and the Kaggle solver itself, run as time-boxed 48-pair probes on Kaggle and Kaggle-like boxes with serving variants (MTP, SGLang, vLLM 0.31, transcript compaction, 4-bit weights; E021/E023/E027). E025's DeepSeek rollouts on training tasks (SFT data for E028) are not evaluations and are left out. Every number below is recomputed from evals/results/*.jsonl, kaggle/runs/ and E027's solver summaries (experiments/E027_l4_throughput/) by reports/build_report.py. Under each run id, traces opens its attempts in the public dataset livobereshka/arc-agi2-eval-traces (every saved transcript on the 120 public-eval tasks) and docs its experiment folder in the GitHub snapshot (private repo).

Scoring convention

  • Primary metric: Kaggle score (pair-weighted). The ARC Prize 2026 ARC-AGI-2 competition page on Kaggle allows 2 attempts per test input; a test output scores 1 if either attempt matches exactly, else 0, and "The final score is the average across all task test outputs". So the Kaggle score = solved test outputs / all test outputs (167 on the public eval set), and a task with 2–3 test inputs counts 2–3 times. All headline numbers, best-value shading, sorting, charts and paired Δs use this metric because it is what the competition scores.
  • Secondary metric: ARC Prize task-weighted. The ARC Prize benchmarking harness (arc-agi-benchmarking, scoring.py) scores each task as the fraction of its test pairs solved and averages over the 120 tasks. ARC Prize's published leaderboard numbers use this convention, so it is shown in smaller muted columns and quoted in parentheses where we compare with ARC Prize's numbers. The two differ only through the 45 tasks with more than one test input; for Table 1 runs the gap is at most 2.3 pp, and Kaggle is the lower of the two in 60 of 74 pass@1/pass@2 values (Appendix).
  • Full set = the official ARC-AGI-2 public evaluation set from github.com/arcprize/ARC-AGI-2 (120 tasks / 167 test pairs). This is the public evaluation set, not the hidden Kaggle test set (240 tasks / 259 pairs) and not ARC Prize's semi-private set.
  • pass@1 = mean over attempts (samples) of the single-attempt score, ± sd over samples. pass@2 = a test output counts if either of 2 attempts is correct (the Kaggle rule); with more than 2 samples it is the mean over all attempt pairs (attempts 0+1 shown as a0+a1). Paired Δ = run minus reference on the same test outputs (Kaggle pass@1, pp), 95% CI from a cluster bootstrap that resamples tasks (all test outputs of a task move together; 10,000 resamples).
  • Completeness rule (Table 1). A run is complete when every counted sample has a record for all 167 pairs. Attempts lost to an API error are scored wrong; a sample with more than 1 such attempt counts as incomplete and the run goes to Table 2.
  • Tokens/attempt = output (completion) tokens summed over all turns of an attempt, over attempts that returned. Cost: rec. = recorded per-call cost (est_cost_usd at off-peak list price incl. input, or OpenRouter's cost_usd); est. = output tokens × list price ($0.60/M Flash, $1.98/M Pro); rental = vast.ai box time from the README (footnoted).
  • Other sets. pilot-26 = the first 15 tasks in sorted id order (26 pairs); dev-56 = E009's stratified dev set (experiments/E009_tool_token_efficiency/dev_pairs.txt); E004a-20 = E004's hard-biased 20-pair subset. Partial runs are scored on their covered pairs only (Kaggle: mean over covered test outputs; task-weighted: a task's score is over its covered pairs and only covered tasks are averaged).

Key findings

Scores are Kaggle (pair-weighted) unless marked task-weighted; task-weighted values appear only where a finding is compared with ARC Prize's published numbers.

  • DeepSeek's new V4.1-Flash-1017 (E029) is more accurate and ~20% cheaper on the same harness; sub80s40 is the new best DeepSeek config.
    • Same harness (sub80s40, persistent-v4), new model: Kaggle pass@1 73.1% / pass@2 82.0% over 2 samples against 66.5% / 76.4% for the old model's E009 sub80s40 (paired pass@1 +6.6 pp [+1.9, +11.4]; task-weighted 74.3% / 82.4%), at 31.7k tokens/attempt (−22%) and rec. $3.59 per sample. The old model's best pass@2 was E009/E011 sub96n's 79.0% at 45.7k tokens. On the 56 long-tail pairs it solves 79.5% (old sub80s40 63.1%).
    • At the tighter s20x60 budget the gain is within noise: 64.4% / 76.6% vs 61.4% / 75.4% (paired +3.0 pp [−1.2, +7.4]) at 26.7k tokens (−19%). The 80k budget is what lets 1017 turn its efficiency into accuracy on hard pairs.
    • A/B on the new model, lean2code ("decide in code" prompt + turns-left note + solve() fallback, persistent-v6): 72.8% / 81.4% at 32.9k tokens, −0.3 pp [−4.9, +4.4] vs plain sub80s40: a tie, so the prompt change buys nothing.
    • Trace reading (E029 strategy_reading.md / strategy_quant.md, not recomputed here): 1017 searches the same way with fewer dead ends; it thinks less per turn (largest turn 12.5k → 9.1k tokens) rather than taking fewer turns, and reaches a runnable candidate early enough that the 60k "submit now" note finds something to submit.
  • E030: a "Reasoning Effort: Minimal" header shortens Flash-1017 without losing accuracy; budget pressure, per-turn caps and prompt lines do not.
    • DeepSeek implements its effort levels as a header at the start of the conversation (high and max prepend "Reasoning Effort: …" text, low adds nothing). --effort-header minimal sends one in the same style as a system message (terse notes, no restating or re-verifying, test ideas in code, submit once train passes). On sub80s40 it scores Kaggle pass@1 74.0% / pass@2 85.0% at 27.4k tokens/attempt (−14% vs plain sub80s40, paired pass@1 +0.9 pp [−3.7, +5.6]) and keeps the long-tail pairs (78.6%).
    • With the s20x60 budget it stacks: 68.0% / 79.0% at 23.3k tokens (−27%), against 64.4% / 76.6% at 26.7k without the header.
    • Budget pressure alone (s20x80: 67.4% / 79.6% at 28.7k, −10%) trims the long tail and loses hard pairs (68.8%). A per-turn thinking cap closed by a "test it in code now" nudge (--cap-nudge, 16k: 31.9k tokens) saves nothing: the model resumes the same deliberation in the next turn. Placement matters: the same brevity request as a user-prompt suffix (E009 lean2brief, old model) cost up to 14 pp.
  • Tools + lean2 prompt beat no tools for Flash; tools alone do not.E004-GL (grid mode, lean2 prompt, low effort) scores pass@1 64.5% over 4 samples against 58.3% for no-tool E001d (3 samples), paired +6.2 pp [+0.2, +12.5], at 49.5k vs 55.7k tokens/attempt. With the plain ARC Prize prompt the same tool harness drops to 51.5% (low) and 47.3% (max, 86.2k tokens): the model reasons by hand, calls the tool rarely and runs out of budget. pass@2 is 75.6% vs 73.3% (mean over attempt pairs). All scores in these findings are Kaggle (pair-weighted) scores.
  • The submit_answer hand-off is what makes the harness both cheaper and more accurate.In E004-GL, 116/668 attempts end without a parsable grid and burn 34% of all output tokens. With submit_answer(expr) the grid is read from the Python session instead of being retyped; in sub80s40 93% of answers arrive that way. sub80s40 reaches 66.5% pass@1 / 76.4% pass@2 at 40.7k tokens (paired vs E004-GL +1.9 pp [−2.1, +5.9]); sub96n reaches 67.7% / 79.0% at 45.7k.
  • Budget notes and soft targets beat hard caps; hard caps cut the long tail.A 64k hard cap (sub64a) scores 57.5% (−7.0 pp [−13.3, −0.9]); on the 56 long-tail pairs (E004-GL's correct rollouts average >40k tokens) it solves 44.6% against 71.4% for E004-GL and 66.1% for sub96n. A 40k cap (s20x40, 1 incomplete sample) falls to 47.8%. A soft target with a looser cap keeps the tail reachable: s20x60 matches E004-GL on pass@2 (75.4% vs 75.6%) at 32.9k tokens (−34%). Thinking-off turns (E010 nt*) save tokens but lose 26–45 pp on dev.
  • E017: a computed perception pack, a roles prompt and session helpers (V3) reach the top tier at fewer tokens; no accuracy change is significant.
    • V3 (all three, harness persistent-v5) scores Kaggle pass@1 69.2% (70.1 / 68.3) over 2 samples against 66.5% for sub80s40 (paired +2.7 pp [−2.4, +7.7]) at 39.5k tokens/attempt (−3%); pass@2 77.2% vs 76.4%. Single samples: V1 (summary only) 67.1% at 37.1k (−9%, shorter correct rollouts: median 22.4k vs 25.4k); V2 (lean2roles only) 67.1% at 42.9k (+6%). One sample swings by several pp (sub80s40's own samples span 63.5–69.5%), so these are 'no harm, slightly fewer tokens' results.
    • Conditional 3rd attempt (only when neither of 2 attempts passes the train check): fired on 24 of 167 pairs and lifts V3's Kaggle pass@2 from 77.2% to 78.4% (+1.2 pp [+0.0, +3.0], 2 pairs rescued) for +12% tokens per pair and $1.05; task-weighted 76.0% → 77.2%. Phase 1 had simulated +2.0 pp [+1.0, +3.2] for +23% tokens 12.
    • The live train check (re-running the answer cell on the training inputs; no model tokens) is a good ranker but a poor gate: P(correct | train pass) = 84% (217/259) on V3's attempts 0–1, 81% for V1, 86% for V2 (phase-1 offline estimate 86% 12); P(correct | train fail) = 27% on V3. The 16% of train-passing answers that are wrong mostly miss something the training pairs do not show.
  • E017 phase 1 (offline, $0): Flash spends its tokens on prose hypothesis search, and the test is almost always novel.
    • Token shares from 48 annotated sub80s40/sub96n traces (population-weighted reader estimates): hypothesis search in prose 51%, perception (reading or transcribing grids, hand counting) 20%, code writing 11%, everything after the first train pass 4%; readers judged about 42% of tokens wasted. Attempts whose longest single turn reaches 30k tokens are 26% correct, against 81% under 10k 13.
    • In 155 of 167 pairs the test input lies outside the training inputs' range on at least one cheap feature (size, colours, component count, border contact, object sizes). The largest failure mode is a rule that fits every training pair and is wrong on the test (12 of 28 failing traces) 13.
    • Restarting attempts that have no train pass by 20–50k tokens loses 7–12 pp pass@1 in simulation (slow successes and dead ends look alike until late), and gating the 2nd attempt on the train check loses 3.8 pp pass@2; only extra attempts where the check fails pay off 12.

  • Public vs semi-private. All full-set numbers are on the public evaluation set.
