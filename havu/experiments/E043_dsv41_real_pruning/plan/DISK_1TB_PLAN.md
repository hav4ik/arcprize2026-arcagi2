# Disk contract for the eight-GPU / 1 TB rental

Updated **23 October 2026** after the user's hardware correction. The active rental has **8 × RTX 6000 and 1 TB disk**. This supersedes prior 2 TB development advice. A 1 TB allocation is a workable planning target when the approximately 510 GB source is kept once and large intermediate copies are avoided; actual free space and exact checkpoint sizes must be measured before downloading.

All GB figures here are decimal, 10^9 bytes. A decimal 1 TB is about 931 GiB. The host filesystem may advertise more space than the container's purchased quota. Use the smaller applicable limit and include existing container/image/cache usage.

## 1. Keep one canonical source

- Pin the exact 1017 revision from TASKS_SERVING.md and retain immutable source bytes/checksums.
- Choose one checkpoint location. Use either the Hugging Face cache snapshot in place or one direct local download. Do not copy a complete snapshot into another directory.
- All TP ranks and any independent TP4 workers read the same files. Separate processes do not need separate model downloads.
- Inspect tensor headers and read only required row/expert extents. Preserve native packed bytes and scales.
- Keep any model revision, tokenizer and weight subset identifiers explicit. Do not economize by deleting source shards still needed for retained-expert selection, original-table controls or export.

## 2. Convert into memory, not a second full disk checkpoint

For the main path, read original packed tensors and convert/repack the active data directly into the runtime representation in RAM/VRAM. Bound CPU staging buffers and per-rank loading concurrency. The extra GPU capacity does not eliminate host-memory peaks during parallel loading.

Do not create by default:

- a second full source snapshot;
- a 300–320 GB serialized converted backbone beside the source;
- a 203 GB full Engram sidecar beside identical source rows;
- all candidate checkpoints or full token/expert activation histories.

If a chosen adapter requires a full Engram sidecar, prefer adding direct source-extent access. A temporary sidecar is acceptable only if a stage-specific measured peak budget satisfies the free-space gate below, and its generated bytes can be removed after the required controls without losing original source data. Do not silently swap the original-table quality baseline for a pruned baseline merely to make storage fit.

The ordinary native Marlin runtime can repack loaded weights in memory; instrument the actual loader and disk writes rather than assuming a library's cache behavior. If the selected path necessarily serializes a full converted model and cannot be changed or staged safely, report that concrete blocker before downloading an additional copy.

## 3. Proposed simultaneous budget

| Component | Planning allowance | Handling |
|---|---:|---|
| Original source | About 510 GB | One immutable copy |
| Compact Engram working table and maps | 45–50 GB | Covers a 32–40 GiB row budget plus mapping/metadata; measure actual bytes |
| One candidate export including its own compact table | 100–120 GB | E64 or E72, one at a time; counts a conservative separate table copy |
| Pilot traces, token shards, row counts, REAP statistics and logs | 20–50 GB | Stream input; use sufficient statistics and bounded logs |
| Software, writable container state and package/build/download caches | 40–70 GB | Measure existing usage; cap caches deliberately |
| **Estimated live payload subtotal** | **715–800 GB** | Does not include the free-space floor |
| **Retained free-space floor** | **150 GB** | Keep free after each large operation |

These are allowances, not measurements or universal minima. For a true 1,000 GB usable quota, the 150 GB floor implies a maximum live allocation of 850 GB. A smaller usable quota reduces the ceiling. If the source or software consumes more than planned, shrink optional corpus/cache/export coexistence first.

Before every large download, conversion or export, compute:

```text
usable_free = min(filesystem_free, remaining_container_quota)
required_free = worst_case_additional_live_bytes + 150_000_000_000
proceed only if usable_free >= required_free
```

`worst_case_additional_live_bytes` includes partial download files, temporary tensors written to disk, staging, both an existing candidate and a new candidate if they coexist, and copy-based finalization. A directory rename on the same filesystem does not duplicate its contents; a copy to another mount does. Record the calculation in `runs/storage/budget.json` before the operation.

## 4. Stage the work

1. **Bootstrap:** inspect the actual quota/mount; record existing used space; download metadata and run small environment/native checks.
2. **Source acquisition:** download exactly one source revision, with bounded concurrency and enough room for partial writes. Verify checksums/manifest before using it.
3. **Engram census:** stream compatible traces; persist counts and coverage summaries. Bound temporary sort/merge space. Avoid copying the full corpus into several agents' directories.
4. **Engram validation:** materialize only the small number of row-mask candidates needed for the next comparison. Prefer virtual masks over full standalone copies where supported; retain original rows for all controls through the canonical source.
5. **Freeze:** keep one chosen compact table/map and its checksum. Prior candidate metrics and keep manifests are small and should be retained; physical tables can be regenerated.
6. **REAP:** collect mergeable sums/counts and optional pair statistics. Do not save every hidden activation. Checkpoint statistics atomically in bounded shards and retain the old/new shard overlap in the space estimate.
7. **Candidate testing:** evaluate E64/E72 through selective source loading before physical export. Keep all keep manifests and metrics; export one selected candidate at a time.
8. **Export:** stream retained experts and rows into a new candidate directory, validate it there, then rename on the same filesystem. Avoid a second full finalization copy. If another candidate export must coexist, recalculate the peak budget; reuse an immutable compact table through a verified reference or hard link only when format/filesystem rules permit.

A regenerable candidate or cache may be removed only after its provenance/metrics are retained and it is explicitly identified as this experiment's disposable output. Preserve source data, user files and the only valid final checkpoint. If an important candidate must be moved off-node, verify the destination copy before deleting the local one; use only a destination the user has authorized.

## 5. Eight GPUs do not require two copies

The intended main configuration is one TP8/EP model, following a short TP4 parity baseline. That shares a single checkpoint path. If two TP4 workers are used instead, share the same immutable source path and compact Engram files; keep each worker's small statistics shards distinct.

File sharing does not necessarily share decoded or pinned host buffers. Check aggregate RAM and pinned-memory use before launching two workers. Avoid scheduling two simultaneous export/conversion jobs just because GPUs are available. The storage gate is a whole-node gate, not one independent budget per process.
